# g5p-3: Define or remove subclass as a build layer

**Severity**: LOW — a cold G5-B author would otherwise invent a subclass subsystem or make the
Battle Mage acceptance case untestable.

**Status**: Verified

**Branch**: `master` (docs-only plan repair; one finding per commit)

**Commit**: this finding's dedicated repair commit (`Define subclasses in Gate 5 model`)

## Evidence

At reviewed SHA `d00c34f77cd9e0c6a72345e45874292aa941f831`, “subclass” appears in the
Wizard battle-axe and Battle Mage cases, but §3 does not define it, §3.8 cannot represent it, and
G5-B does not require subclass rules.

## Predicted observable failure

The eventual class catalog either silently adds an unreviewed subsystem or drops subclass from the
examples, allowing the same build to receive different entitlements depending on implementer.

## What

One proposed legal build path lacks an owner, schema position, admission rule, and deliverable.

## Approach

Define subclass as an optional class-owned specialization within a class level track, with catalog
prerequisites, feature grants/replacements, and no independent level budget. Add it to the logical
record, admission boundary, and G5-B deliverables.
